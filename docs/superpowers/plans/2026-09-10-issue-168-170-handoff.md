> **For agentic workers:** Steps use checkbox (`- [ ]`) syntax for tracking. Tasks 1 and 3 are independent of each other; task 2 is an investigation with no guaranteed landing point and should not block the other two.

**Goal:** Close #170 by making the walker-array indirection conditional on Numba's freeze limit, find the trigger behind #168, and put a consolidated before/after wall-clock comparison into the 0.11.0 release note so a reader can see what upgrading buys without opening the profiling report.

## Task 1 — #170: make the walker-array indirection conditional

**The defect.** #162 moved the CSR walker arrays and the loop-Jacobian index arrays from module-level globals to function arguments so Numba could cache the kernels. Its diagnosis is correct and its own title says "of large models", but the remedy was applied unconditionally. Numba freezes a global array into the IR only below `size_limit = 10**6` bytes, `numba/core/base.py`, `make_constant_array`; below that the function is both optimally compiled and cacheable. So for every model whose walker arrays are under the limit the change bought a property that already existed, and charged for it.

**Measured cost**, Cookbook IES `loopeqn=False`, medians of three alternating rounds:

| | 0.10.2 | 0.11.0 | |
| --- | ---: | ---: | --- |
| cold compile | 295.3 s | 343.9 s | 1.17 slower |
| F eval | 731.6 µs | 864.8 µs | 1.18 slower |
| second import, cache hit | 1.6 s | 1.5 s | **both cache, 1236 `.nbi` each** |

The last row is the point: 0.10.2 cached this module completely, with no `Cannot cache` warning.

**Where the cost lands.** Splitting the cold import by function on 0.10.2 shows compilation concentrated in the two dispatchers, not in the kernels:

```
import 271.9 s | 1236 functions
    inner_J        416.06 s      <- timers nest; read as weights
    inner_F         59.20 s
    every other kernel under 3.5 s
```

and those are exactly the signatures that grew: `inner_J` 213 to 227 arguments, `inner_F` 213 to 219.

**The fix.** `walker_args` is built as a set of names at `Solverz/code_printer/python/module/module_generator.py:90` and consumed by `print_F` at `:97` and `print_inner_F` at `:104`; the Jacobian side carries its own list through `module_printer.py:369`, `:482`, `:487` and the signature construction at `:1070`, `:1163`, `:1174`, `:1229`. Issue #162 notes that "the parameters shadow the globals", so **dropping a name from that set makes the generated body fall back to the module-level global with no other change**. The arrays are already emitted as globals from `setting` at `module_generator.py:175-177`.

- [ ] Add a module-level constant, `_NUMBA_FREEZE_LIMIT = 10**6`, with a comment naming `numba/core/base.py` `make_constant_array` as the source and stating that it is a local variable there and therefore not importable.
- [ ] At `module_generator.py:90`, keep a walker name in `walker_args` only when its array is at or above the limit, or is not C or F contiguous. A non-contiguous array is never frozen whatever its size, so it must take the argument path too.
- [ ] Apply the same condition to the loop-Jacobian `_sz_loop_jac_row_<N>` / `_sz_loop_jac_col_<N>` arrays on the `module_printer.py` side.
- [ ] Keep the behaviour identical when the model mixes sizes: a small array may stay global while a large one in the same kernel becomes an argument. A frozen global is not a dynamic global, so the function stays cacheable as long as every array above the limit is an argument.

**Acceptance.**

- [ ] `pytest tests/ Solverz/` passes, including `test_loop_eqn_walker_above_one_megabyte_is_cached_by_numba`, which is the #162 regression test and must still see no `Cannot cache` warning.
- [ ] A new test asserts the other side: render a model whose walker is **under** the limit, assert the generated `inner_F` signature does **not** carry `_sz_csr_*`, and that importing it still writes a `.nbi` and raises no `Cannot cache` warning.
- [ ] On the Cookbook IES `loopeqn=False`, `inner_J` is back to 213 arguments and `inner_F` to 213.
- [ ] F evaluation on MATPOWER case118 returns to the 0.10.2 figure. Measure by rendering the same model under both and timing `mdl.F` alternately; 0.10.2 gives about 5.4 µs and 0.11.0 about 6.6 µs today.
- [ ] The two cases whose walkers exceed the limit, case_ACTIVSg70k at 1.8 MB and case_SyntheticUSA at 2.1 MB, are unchanged, since they already take the argument path. Their F ratios today are 1.01 and 1.07, that is, no penalty either way.

**How to measure without fooling yourself.** Every wrong number in this project came from a single sample. Alternate between the two builds, repeat at least three rounds, and compare minima as well as medians. For the microbenchmark of frozen-global against argument, keep every array under 10**6 bytes or the global is not frozen and the comparison measures nothing, and do not allocate extra copies of the arrays to test a third variant in the same process.

## Task 2 — #168: find what puts two `SetIdx` of one label in one body

**The state.** A canonical Jacobian expression of one `LoopEqn` can contain two `SetIdx` that share a label and bounds but carry different tokens, that is, indices produced by two different `Set` objects. Reported by `check_canonical_invariants` on the cookbook `test_ies_legacy_module` job:

```
index label 'i_q' is carried by 2 unequal objects: SetIdx(i_q, (0, 5), 9) vs SetIdx(i_q, (0, 5), 3)
index label 'j'   is carried by 2 unequal objects: SetIdx(j, (0, 8), 1) vs SetIdx(j, (0, 8), 7)
```

**Severity.** Latent, not active. The analyzer compares indices by label since the fix in 0.11.0, so it reads the two as one and the Jacobian is correct; a finite-difference check of the same model shape agrees to 2e-9 and the cookbook suite is green. It would become wrong if two `Set` objects of one label held **different members**, and nothing in the module can detect that.

**What is ruled out.** Three consecutive `PowerFlow(...).mdlpf_loopeqn()` builds in one process raise no warning. One build, and three builds of different sizes, are clean. The platform is not involved.

- [ ] Reproduce first. The token spacing, `j` at 1 and 7 and `i_q` at 3 and 9, says two `PowerFlow`-shaped constructions bracket one other `IndexSet`, and SolUtil's `mdlpf_loopeqn` creates five sets per build. Build the IES the way `test_ies._build_ies_model` does and print the token of every `SetIdx` as each component is added.
- [ ] Find the first expression that carries two. `check_canonical_invariants` already reports it; call it earlier, per `LoopEqn`, rather than only on the canonical derivative.
- [ ] Then decide where the fix belongs. If a body is reused across two model constructions, the fix is in whoever caches it. If one `Set` is rebuilt where it should be reused, the fix is in the component that builds it. Solverz is only at fault if the token is being lost or reassigned.
- [ ] Keep the guard whatever the outcome, and consider promoting it from a warning to an error once no model triggers it.

## Task 3 — a before/after table in the 0.11.0 release note

**Why.** The 0.11.0 notes state effects inside individual bullets, so a reader has to assemble the picture. The measurements exist; put them where the release is described. Note the tag is already cut, so this reaches the documentation and not the published wheel.

**Power flow.** From `pf_profile/results_0102` and `results_0110`, both ladders run back to back on one machine. `nr_method` solve from the case-file start with KLU:

| case | buses | 0.10.2 | 0.11.0 | gain |
| --- | ---: | ---: | ---: | ---: |
| case_SyntheticUSA | 82 000 | 11.5 s | 826 ms | 13.9 |
| case_ACTIVSg70k | 70 000 | 10.8 s | 723 ms | 15.0 |
| case_ACTIVSg25k | 25 000 | 535 ms | 158 ms | 3.39 |
| case_ACTIVSg10k | 10 000 | 95 ms | 57.8 ms | 1.64 |
| case_ACTIVSg2000 | 2 000 | 16.3 ms | 11.3 ms | 1.45 |
| case9 to case57 | 9 to 57 | | | 1.24 to 1.29 |
| case39 | 39 | **did not build** | 0.218 ms | — |

- [ ] Say plainly that three cases between 1 000 and 3 000 buses are slower, case1354pegase at 0.86, case2869pegase at 0.92 and case1888rte at 0.94. A release note that reports only the wins is not a record.
- [ ] Give the per-iteration split for the large end, since it says where the gain comes from: on case_SyntheticUSA the LU drops from 1.84 s to 63 ms, a factor of 29, while F and J move by 1.07 and 1.10.
- [ ] State that `nnz(J)` is identical on all twenty cases both releases build. That is the check that the sparsity analyzer still reserves the same pattern after the `Set` and `LoopEqn` fixes.

**Other model kinds.** Do not let the power-flow number stand for the release. Two separate things exist and must not be conflated.

- [ ] The Cookbook IES, a differential-algebraic electricity, heat and gas model integrated by Rodas, is the one non-power-flow model with a true version comparison. Medians of three alternating rounds, `loopeqn=False`: F 731.6 against 864.8 µs, J 3445 against 3153 µs, cold compile 295.3 against 343.9 s. On this model the release is a small net loss at run time, and the note should say so.
- [ ] Do not put SolPSDyn, the gas-network method of lines or the IES iteration matrix in the note. Only a matching on and off comparison exists for those, run within 0.11.0, which is not a version comparison and would read as one beside the tables above.
- [ ] Do say, in one sentence, that the large gain is specific to power flow, so the headline is not read as applying to every model. The mechanism carries the caveat on its own: the row matching pays off in proportion to how empty the structural diagonal is, and a `LoopEqn` power-flow Jacobian is the extreme case.
- [ ] Do not re-measure Model 1 of #134, the Barry Island fault IES, without building a driver for it; it has none, and run 1 of that issue remains its only measurement.

**Sources.** Power-flow figures are Table 10 of `pf_profile/report/main.pdf` and the JSON under `results_0102` and `results_0110`. The IES figures are in [benchmark run 2 and its corrections](https://github.com/smallbunnies/Solverz/issues/134). Take them from the corrections, not from the original run 2 comment, whose symbolic-phase numbers were retracted.
